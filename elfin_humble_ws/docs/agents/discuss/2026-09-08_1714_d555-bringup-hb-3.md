Why this is needed. The current transform `eef_mount_adapter` to `camera_link`
is `0.013 0.097 -0.021`, rpy `0.03770 1.36345 1.57080`. Its provenance is
`camera_mount_origin.xacro`, header "Saved by `eof_mount_stack_tune_gui.py`",
and `NOTES.md` attributes it to the "D435 mount GUI". That is visual GUI tuning
against a D435 body origin, not metrology. The mount is physically correct for
D555, but a D555 body origin sits elsewhere inside it, so the value is suspect.
`motion_compensation.md` derives sensor pose from FK plus this fixed transform,
so it is load-bearing for motion compensation as well as for cargo geometry.

Method summary, with the plan as the authority:

1. Three distinct static arm poses that all observe a common flat floor region.
   Capture D555 depth and Mid-360 simultaneously at each.
2. Fit a plane to the floor points from each sensor independently, transform
   both into `elfin_base`, and report plane-to-plane **offset in mm** and
   **angle in deg** per pose.
3. Interpret the pattern. An offset roughly constant across poses indicates a
   mount **translation** error. An offset that varies with pose indicates a
   mount **rotation** error. State which pattern the data shows; this
   distinction is the main deliverable.
4. Report the residual against the current GUI-tuned value so a CAD-seeded
   replacement can be judged later.
5. The 2026-09-08 screenshot showed doubled edges on the Mid-360 view of an
   upper rail. State whether that is RViz `Decay Time` accumulation or genuine
   motion distortion from absent deskew. Do not implement deskew.

Pass condition: nine numbers (three poses times pose id, offset, angle), the
translation-versus-rotation conclusion, and the smearing verdict.
