## 1. Product decision and scope

Reset means the current OCC is no longer trusted for placement. It can be triggered by a detected scene/map inconsistency, a geometry/config/clock identity change, or an explicit reset request. The triggering detector is outside this work: tests inject the reset event through the existing service. The contract covers OctoMap observation, Surface/ROI/free-space requests, the placement consumer, and the planning admission boundary. It does not authorize robot motion or production migration.

An old immutable view may remain allocated while an owner holds it. Its bytes remain charged to that owner until the final reference is released. That view is immediately unusable for placement once reset invalidates its epoch. The 3,363,936-byte old view and 72-byte Surface buffer observed in S3 must be investigated by identity and owner trace; their size or mere survival at the reset instant is not a leak verdict. A buffer still charged after the last owner has released it is a failure.

## 2. State machine and linearization

| State | Entry | New read/acquire | Writes | Downstream |
|---|---|---|---|---|
| `VALID(e)` | New-epoch map meets §3 readiness and is atomically published | Permit only `e` | Accept `e` | May compute after fresh input checks |
| `INVALID(e+1, reason)` | Reset commits invalidation and increments epoch atomically | Return `INVALIDATED`/`NO_DATA`, no old data | Reject old `e` with `EPOCH_MISMATCH` | Cancel/hold placement and planning |
| `BUILDING(e+1)` | Empty/new store is ready for new observations | No placement reads; diagnostic status may report progress | Accept only `e+1` | Continue hold |

`INVALID` begins at the reset linearization point **before** old state can be exposed to another new request. The state change, epoch increment, invalidation event and old-snapshot unpublishing are one logical transition. An in-flight integration from `e` either commits before that point or terminates `EPOCH_MISMATCH`; it must never appear in `e+1`. An acquire/read that linearizes after it cannot obtain `e`. A request that acquired `e` before it may finish internal work, but its final response and any placement/planning commit require a second state/epoch check. If the reset won, return `INVALIDATED` with no usable candidates; if the result was already committed, the downstream invalidation event revokes it before any later planning admission. This defines the race without a global long-held lock.

`reset_id` makes a duplicate reset idempotent within an epoch. A later distinct reset increments epoch again and invalidates the rebuilding map. Every status and result carries state, epoch, map/observed revision, geometry/config/clock identity, reset reason, and a monotonically increasing validity generation. An explicit validity/status service plus a latched invalidation publication (or equivalent replayable event) lets a restarting consumer observe the current state; a transient event alone is insufficient.

## 3. Recovery and downstream admission

Transition `BUILDING(e)` → `VALID(e)` only after at least one accepted **new-epoch** observation, a published snapshot with matching geometry/config/clock identity, successful integrity check, and age ≤1 s at publication. A floor prior or old snapshot cannot satisfy readiness. The owner must document the exact observation/integrity predicate and expose it in health/status. A further reset restarts this process.

Placement stops new computations as soon as invalidation is observed. It invalidates queued and cached Surface, ROI, free-space candidates and derived placement results from older generations. A request in progress may complete its internal calculation, but its response must be tagged invalid and must not become a valid placement result. Planning admission checks current validity and epoch both before planning and before committing a plan or motion request. A mismatch pauses admission and discards the candidate/plan. A delayed old response cannot reopen the gate.

Recovery requires a fresh `VALID(e)` OCC read and a new sample of robot joint/EEF state (and any other dynamic planning input used by that path) **after** the validity transition. Each sample must pass its existing timestamp/TF contract; missing or stale inputs keep the gate closed. Placement candidates and plans are recomputed from these new inputs. This contract stops issuing new motion commands; handling a command already executing follows the production orchestration safety boundary and must be reported as `execution_active` rather than silently canceled or assumed safe.

## 4. Concurrency and ownership implementation requirements

Use a short validity/epoch critical section for transition, acquire, and commit checks. Do not hold it during store integration, Surface/ROI work, ROS waits, placement, or planning. Document a total order for any state, repository, cache and store locks; avoid nested locks where possible. Reset cannot wait for all old readers to release. Every error, timeout, invalidation and cancellation path releases leases and response buffers in `finally`/RAII. The source must state the lock order, linearization points and owner of every retained object next to the relevant interfaces.

Resource reporting separates retained store state, live lease, client-held view, external Surface buffer and in-flight response. Shared objects are counted once. During reset, a held old object remains charged to its current owner and is marked invalid; after the last owner releases it, its class returns to its applicable baseline. If a periodic sample sees 72 bytes, retain object id, allocation/release time, owning handle, epoch and reference lifecycle to distinguish a legitimate overlap from a surviving final release.

`INVALIDATED`/`EPOCH_MISMATCH` are expected outcomes only when raw event timestamps prove reset won the relevant linearization race. A status code alone never grants pass: judge must also prove no usable payload and no downstream admission. After a new valid map, these codes are failures for normal requests. `NO_KNOWN_FREE` remains a valid geometric outcome when independently supported; `NO_DATA` during invalidity is not a successful placement.

## 6. Runner and judge changes

Implement versioned artifacts and commands under `src/uld_occ_observer/test/benchmark/`. Required entry points: `python3 .../reset_campaign.py --mode rehearsal|score --manifest <frozen-input> --out <new-run>` and `python3 .../reset_judge.py --run <new-run>`. Keep the existing `COMMANDS.sh` build, rehearsal, freeze, O9, score, judge and replay commands; add `reset-rehearsal`, `reset-score`, `reset-judge`. The implementation owner may choose internal module names, but these CLI interfaces and exit codes are fixed: zero only for a complete pass, nonzero for fail or incomplete evidence, with `not_evaluated` named in the JSON report.

Runner schedules by integer request index and absolute monotonic deadline; it must not use a `while now <= end` loop to create an unbounded last request. Persist planned/actual send times, reset linearization marker, response receipt, release, downstream rejection/admission and robot-state acquisition. Stop generating after the frozen index set; a race can yield ≤2 extra IDs per stream, each labeled and retained. Preserve complete response content/hashes for one bounded failing case, not just a summary. Judge computes planned count, actual count, overrun, post-deadline completions, one-terminal closure, per-ID timing and identity from raw records. It must reject missing/duplicate IDs, truncated payloads, forged summary, a stale plan admission, wrong epoch, absent robot refresh, premature owner decrement, residual after final release, and an overrun of 3 IDs. Healthy overrun 0 and 2 fixtures must pass. A 2-ID overrun with one failed query must fail.

Reset tests must use barriers at named stage boundaries, not sleeps as proof of order. Record lock wait and stage timestamps. Verify no deadlock in all pairings; a timeout is a failure with preserved trace. Rehearse startup/ready/runner/judge against the same binaries without consuming scored samples; score only after fixed candidate and frozen manifest/hash. The judge reads artifacts from disk and returns a nonzero exit code on failure. No threshold is changed after scoring starts.

## 7. Evidence and budgets

Each new run writes `manifest.json` (product/tool/plan SHA, dirty state, environment, seed, input hashes, clock domain, owner/model, commands, start/end, gate and teardown status), `events.jsonl` (T1 boundary events with request/epoch/generation/stage/status/time/resource), raw input/output hashes, `verdict.json`, and a `FINAL_REPORT.md` with pass/fail/not_evaluated for V1–V3/P/H/L/R and historical O8/O5/O6 separate. For a failed case, freeze a T2 bundle before teardown/retry; target the trigger ±5 s, include the exact upstream request, validity transition, ownership changes and downstream acceptance/rejection. If this cannot reconstruct the case, mark `capture_complete=false`, fix capture, and do not spend another scored unit on the same gate.

| Boundary | T1 | T2 trigger and payload | Window and cap | Replay |
|---|---|---|---|---|
| Observation/reset | ID, epoch, state, transition time | mismatch/timeout: input, receipt, reset reason, store identity | ±5 s, 64 MiB/case | `reset_campaign.py --mode replay --manifest <case>` |
| Repository/Surface/ROI | lease, page, cache, owner bytes, result identity | stale accepted, leak, timeout: lossless request/page and owner trace | ±5 s, 128 MiB/case | same replay entry |
| Placement/planning admission | OCC and robot-state stamps, generation, decision | old admission or premature resume: candidate/plan identity and gate state | ±5 s, 32 MiB/case | same replay entry |
| Scheduler/judge | planned/actual times, ID closure, count | overrun, gap, forged summary: raw schedule and terminal records | whole bounded window, 32 MiB/case | `reset_judge.py --run <case>` |

Cap each case at 256 MiB, each run at 2 GiB and this campaign at 8 GiB; compress losslessly and stop before the cap would omit replay-critical data. T1 always on; T2 only for failure; T3 only after T2 identifies a module and is excluded from timed comparison. Record T1 overhead using 30 paired ON/OFF samples; each of four existing O9 operations must remain ≤1.10 ratio. Keep failed artifacts in `docs/status/evidence/`; do not overwrite S3 run01. No automatic cleanup of failed bundles before review.
