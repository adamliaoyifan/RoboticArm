## Summary

Reviewed `docs/plans/d555_sim_depth_pipeline_execution.md` R2 against the canonical sensor pipeline. R2 is a lifecycle protection gate for PF-R10/PF-R7 fixed revisions, not the RGB-D stream contract. The simulation stream contract is already defined by the plan objective and fixed facts: Gazebo emits colour, 32FC1 metre depth, and CameraInfo on one grid; a single-stream adapter converts depth to 16UC1 millimetres; the preprocessor exact-pairs colour, aligned depth, colour CameraInfo, and aligned-depth CameraInfo; consumers deproject selected pixels with same-acquisition K and stamped TF. A clarifying plan amendment should state this near R2 or DSIM-INTEGRATION so future owners do not treat R2 as permission to use D555 native depth, `/camera/d555/depth/color/points`, Gazebo camera clouds, approximate pairing, or hardware compressed transport in simulation.

## Acceptance

- R2 remains a dependency/lineage gate only; satisfying or waiving it must not change the RGB-D data path.
- Simulation uses `/camera/color/image_raw` plus adapted `/camera/depth/image_raw` as the Gazebo binding, with four-product exact identity and a configured common colour optical frame.
- Live D555 remains separate: colour compressed JPEG plus aligned-depth lossless PNG into the same preprocessor core, with no native depth or `/camera/d555/depth/color/points` as canonical input.
- DSIM-INTEGRATION must certify the simulated depth-image path only, and must not claim PF-R10/PF-R7 pass, hardware hand-eye validity, or D555 hardware stream certification.

## Risks

- The plan text names "External gate R2" in DSIM-INTEGRATION but does not restate the stream contract there. That can confuse scheduling/lifecycle readiness with data-path authorization.
- The latest PF-R7 lineage notes waive the DSIM wait for a passing PF-R7 audit but also say DSIM generation 1 is still not claimable; dispatch readiness still needs an explicit reviews action, not an implementer interpretation.
